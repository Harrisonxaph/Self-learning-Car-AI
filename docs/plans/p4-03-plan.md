# P4-03 plan: save and load custom tracks

> **Status: plan only, for Codex review and the owner's merge. Implementation needs its own owner authorisation.**
> - **Authorisation:** the owner's "Continue development" (2026-11-12, after #168 merged), read as the next Phase 4 step. P4-03 needs P4-01 (Complete) and P4-05 (merged, In Review, device checks outstanding). As for earlier items it is read as authorising a **plan only**.
> - **Scope:** the roadmap entry and issue #30: store custom tracks in `localStorage` with JSON export and import, using the same safety rules as models, and make a saved custom track selectable in the P4-05 evaluation runner. **Not** in scope: training on custom tracks (training uses training circuits only), a custom track in any study (E3, E5, E6 and P5-04 use built-in circuits from the command line), editing the built-in circuits, zoom and follow (P4-07), Silverstone (P4-06), any physics change, any learning claim.
> - **Lessons carried from P4-04 and P4-05:** the held-out boundary is the integrity of every generalisation claim, so a track a person makes or imports must never be able to *be* a held-out circuit (an identical copy, or a copy under another ID), and the page must not reveal which circuit it matched; validate everything a person can produce or paste (a hostile file is a message, never an exception); one damaged entry never hides another; entries bind to what produced them; results are labelled by what they are; never infer owner device checks.

## 1. What P4-03 must deliver (ROADMAP, issue #30)

- **Description:** store custom tracks in `localStorage` with JSON export and import, using the same safety rules as models, and make saved custom tracks selectable in the P4-05 evaluation runner.
- **Acceptance:** round trip identical; invalid or corrupt tracks rejected safely; a saved custom track can be chosen as an evaluation track in P4-05 (**completing the custom-layout part of the Phase 4 acceptance**).
- **Tests:** unit: track store. E2E: save, reload, load. E2E: evaluate a saved model on a saved custom track.

## 3. Design

- **`src/persistence/trackStore.ts` (new, pure over an injected storage).** The same shape as the model store: `sdae:track:<id>` per track and `sdae:tracks:index`, a hint the store reconciles by scanning (a save that failed between the two writes, a damaged index). Operations: `list`, `load`, `save`, `remove`, `exportTrack`, `importTrackText`, each returning a result with a message and never throwing. Every access is wrapped; a throwing, full or empty store gives a message. All-or-nothing write; one damaged entry is listed as damaged and never hides or deletes another save. **Limits:** at most 20 saved tracks (a further save asks the person to delete one, as for models) and **256 KiB** per track document (a 2,000-point track is well under this; the cap is checked before parsing work, so a huge file is a cheap refusal). Storage keys never collide with models, checkpoints or any other key.
- **What is stored.** The **track document** (the existing format, validated by `validateTrack` on every save, import **and load**, so a hand-edited storage entry is caught) plus, when the track came from the editor, the editor's **source state** (points, width, gate spacing, start, name) under `editor`, so **Edit again** reopens exactly what was drawn instead of a lossy rebuild. A track imported without source state is drivable and evaluable but not editable (decision 3). The stored text is **canonical** (fixed key order, numbers printed as `JSON.stringify` does), so export, import and export again is **byte-identical** (the roadmap's round-trip criterion), whatever key order the file had.
- **Identity and the held-out boundary (test-enforced).**
  - A saved track's `id` must not equal any built-in circuit ID (training, validation or held-out): a file claiming one is refused, and the message says only that the ID is reserved, never which split it belongs to.
  - **Every save, import, load and evaluation resolves the track through `assertEvaluationTrack`.** A layout whose geometry equals a built-in circuit, **held-out above all**, is refused with one generic message ("This layout matches a built-in study circuit and cannot be saved or evaluated here"): the page never names the circuit, so it cannot be used to probe which layouts are reserved. (The refusal exists because evaluating a copy of a held-out circuit in the browser would be a look the studies forbid.) A geometry that equals a built-in **training or validation** circuit is allowed and labelled as that circuit's layout; it is not a different circuit.
  - The track store and its page code never import `heldOutTrack` or the study gate; no module is added to that source-scan allowlist. `assertEvaluationTrack` is already allowed where it is used; the store reaches it through one small function in `trackSplits.ts` (`classifyCustomTrack`, which maps `TrackLeakageError` to the generic message) so no new module names a held-out concept.
- **Export and import.** **Export** downloads one track as `<id>.json` (`downloadJson`). **Import** reads a file the person chooses (a file input; the same size cap, checked before parsing; UTF-8; the `format` and `schemaVersion` of the track format are required for an imported file), validates it with every message `validateTrack` gives (the first three shown with "and N more", as for models), then applies the identity and boundary rules above and saves it. An id that is already saved is not silently overwritten: the same geometry is "already saved" (no change), different geometry under the same id is refused with a message asking for another name (decision 4). An imported `split` label is **ignored**: a custom track has no split, and a file cannot relabel itself.
- **The editor page.** A **Save track** button (with the name field the editor already has), a **Saved tracks** list (name, gate count, length, saved date, a damaged entry listed with its reason), and per saved track **Edit**, **Drive**, **Export** and **Delete**, plus **Import track**. All controls at least 44 px and keyboard accessible, like the rest of the editor; messages announced politely to screen readers; focus stays on the control just used (the lesson from #168). Saving a track that is not valid is refused with the validator's first message; **Save** is enabled only for a valid, closed loop.
- **Evaluation (the P4-05 plug-in point).**
  - `?mode=evaluate` gets a third checkbox group, **Your saved tracks**, from the track store. Each entry is labelled *custom layout (not a built-in circuit, not held-out)*. The runner is unchanged except that `resolveCircuit` gains a source: a saved track's ID resolves through the track store, is re-validated and re-classified on every run, and its **geometry hash is the entry's `contentHash`**.
  - **The entry format gains one split value, `custom`.** Entries for built-in circuits are unchanged and still validate exactly as before; an entry whose `track.split` is `custom` carries the track's id, version and content hash. The model schema version and the protocol `p4-05-evaluation-v1` are unchanged (one more allowed split value, no change to rows, summary or limits); an older copy of the app reads such an entry as an unrecognised claim (kept, warned, not shown), which is safe.
  - **Validation of a custom entry** checks everything it checks for a built-in one except the registry lookup, which has nothing to look up: when the saved track is still stored with the same content hash, the start poses and gate count are checked against its geometry exactly as for built-in circuits; when it has since been deleted or edited, the entry is checked structurally (its recorded start poses stay bounds-checked against the protocol, the hash is recorded) and the page says **"this track is no longer saved"** beside the result. That is weaker than the built-in check and is stated, not hidden (decision 5).
  - Results for custom tracks are stored in the model's `evaluation` field exactly like others, under the same 50-entry cap (recognised entries only, enforced only on append), and **never feed the dashboard, a ranking, a comparison or a selection**.
- **No change to the trainer, the split manifest, the held-out gate or the study code.** Training still offers training circuits only; a custom track is never a training target (decision 6). No new storage for models. The editor's existing **Drive it** and **Back to editing** are unchanged.

## 4. What is deliberately not claimed

A saved custom track is well-formed and drivable by the validator's rules. It is not interesting, fair or good for training, and evaluating a model on it shows how that model drove there from five starts, nothing more. A custom layout is **not** a held-out circuit and nothing here is an unseen-track generalisation claim: the person who drew it may have trained on something similar. Custom tracks are one driving direction (counter-clockwise on the screen, as the editor builds them). Real iPad and iPhone behaviour is established only by the owner's device checks. No learning claim is made.

## 5. Decisions for the owner (defaults proposed; each routine unless changed)

1. **Browser storage keys** `sdae:track:<id>` and `sdae:tracks:index`, at most 20 saved tracks and 256 KiB each, with the model store's safety rules (injected storage, all-or-nothing writes, damaged entries listed, never deleted).
2. **Export and import one track at a time as a JSON file**, in the existing track format; the file's `split` label is ignored.
3. **Imported tracks without editor source state are drivable and evaluable but not editable** (recommended, rather than reverse-engineering control points from boundaries).
4. **An ID that is already saved is never silently overwritten:** the same geometry is "already saved"; different geometry under the same ID is refused with a message.
5. **One new allowed `track.split` value, `custom`, in evaluation entries**; the protocol and model schema versions stay as they are. Entries for a deleted or edited custom track are validated structurally and labelled "no longer saved".
6. **Custom tracks are never training targets, never used by a study, and never ranked**; training and the studies use built-in circuits only.
7. **A layout identical to any built-in circuit is refused with one generic message** that does not name the circuit (the held-out boundary); a layout identical to a training or validation circuit is allowed and labelled as that layout.

## 6. Tests

- **Unit (`trackStore`):** save, list, load and remove against a fake storage; the round trip **export, import, export is byte-identical** for editor-made tracks, for a built-in-circuit-shaped layout, and for a file whose keys are in another order; invalid, truncated, oversized, non-JSON, wrong-`format`, wrong-`schemaVersion` and wrongly typed input rejected with messages and **no write**; every `validateTrack` rule reachable from import (a corner too tight, a gate off the boundary, a start off the road) shown with its message; the 20-save cap and its message; a 256 KiB cap tested at the boundary; a throwing, full or disabled storage gives the model store's messages and stores nothing; a damaged entry and a damaged index never hide or delete another save; a hand-edited stored track that no longer validates is listed as damaged and never loaded; keys never collide with models or checkpoints.
- **Held-out boundary:** a file whose geometry equals **each** built-in held-out circuit is refused on import, on save, on load from storage and on evaluation, **with the generic message and no circuit name**, and that refusal happens before any episode runs (the P4-05 zero-episode spy); the same for a copy under a different ID, an ID equal to a held-out circuit's ID, a copy with a different `split` label and a copy with reordered keys; a layout identical to a training or validation circuit is allowed and labelled; source scans show the store, the page code and `resolveCircuit` never name `heldOutTrack`, and the allowlist is unchanged.
- **Evaluation integration:** evaluating a saved model on a saved custom track is deterministic (twice, identical entries but for `recordedAt`) and the entry replays; the entry validates with its track present, is structurally validated and labelled after the track is deleted, and is refused when its recorded start poses leave the protocol bounds, when its hash is altered while the track is present and when it is bound to another champion; **entries for built-in circuits validate exactly as before** (the P4-05 suites unchanged), and an entry with an unknown split is still refused; the cap, byte-identical refusals and the legacy-array rules from #168 hold with custom entries included.
- **Page wiring (Node, fakes) and E2E (Chromium and WebKit, desktop, phone and tablet):** draw a track with pointer events, name it, **save, reload, see it in the list, load it** (Edit, Drive); export a track and import it back (`setInputFiles`), identical; import a bad file and see the message with nothing saved; delete; **evaluate a saved model on a saved custom track** and see the table, reload and see the stored result; no held-out circuit and no matched-circuit name appears anywhere; focus stays on the control used; 44 px controls and no horizontal scroll at 320 px.
- **Mutation checks** during implementation: removing the geometry classification, the generic-message mapping, the size cap, the canonical-order output, the load-time re-validation and the entry's custom-split check each fails a test.
- Not tested here: a physical device, and any statistical claim.

## 7. Owner checks (iPad and iPhone, before a completion request)

1. In `?mode=edit` draw and name a track, press Save track, reload the page and see it in Saved tracks; Edit it and Drive it.
2. Export it (the file appears in Files or Downloads) and import it back; delete it.
3. In `?mode=evaluate` pick a saved champion, tick one of your saved tracks and run: the table appears, labelled as a custom layout; reload and the result is still there; nothing scrolls sideways and controls are easy to tap (44 px).

## 8. Limits

Twenty tracks, 256 KiB each, in the browser's own storage; clearing site data deletes them, so export keeps a copy. A track evaluation is one model, one layout and five starts: behaviour, not evidence. Results can differ between browsers and engines. ST1 to ST5, the three-split boundaries, the study held-out gate and ledger, every existing record and the E3 protocol are untouched.
