## 1. What P3-07 must deliver (ROADMAP, issue #27)

- A **debug panel with FPS and mean step time**. The FPS readout (opt-in `?debug=fps`) already exists from P3-03; the roadmap keeps the step-time readout, and the named-device figures, as P3-07 requirements.
- A separate, **versioned generation-boundary checkpoint**: the population, champion, next-generation index, all PRNG states and caches, full configuration, track versions and metrics.
- **Save periodically while active.** Tab-hide delivery is not guaranteed, so a hide is a best-effort extra save, never the only one.
- **Champion JSON alone cannot resume evolution** (P3-05's saved champions stay controller-only; the checkpoint is a different document).
- **Handle quota and storage failures and offer file export.**
- **Acceptance:** metrics visible on a named device and browser with the population, track and render mode recorded; **resuming at a generation boundary matches an uninterrupted run**; storage failures leave training usable and are reported.
- **Tests:** integration for checkpoint and resume determinism, PRNG state recovery and unavailable or quota-limited storage; **manual** iOS background/resume and termination recovery checks.

## 3. What a checkpoint must hold, and what it cannot

At a **generation boundary** (the instant `finish()` has scored generation g and started g+1) the whole future of the run is determined by: the configuration, the environment (physics, timestep, sensors), the track versions and hashes, the genomes of generation g+1 (**the population**), `run`'s four state words, the next generation index, and the history. There is **no cache**: the generator has no spare draw (`gaussian` consumes whole draws), and the per-transition generators are created fresh from `run` each time. The plan says so, tests it (§7), and records `rngStreams` (`RNG_STREAMS`) and the algorithm name so a reader can refuse a checkpoint made under a different draw layout.

A **mid-generation** state (cars partway through an episode) is **not** saved: it would need every car's vehicle and episode state, and the roadmap asks for generation-boundary resume. After a resume the interrupted generation is **re-run from its start**, which is exact because it is determined by the population.

## 4. Design

- **`src/training/trainer.ts`: `createTrainer(input, environment, resume?)`** (or an exported `resumeTrainer`). `resume = { generationIndex, genomes, runState, history }`: it validates the setup exactly as for a new run, restores `run` with `restoreRng`, starts generation `generationIndex` from the genomes, and keeps `history`. Everything else is unchanged, so a fresh run is byte for byte what it was (the existing golden and determinism tests guard that). Also `trainer.checkpointState()` returning the boundary state (a copy; never aliasing live arrays).
- **`src/persistence/checkpointFormat.ts` (new, pure):** the document `self-driving-ai-evolution/checkpoint`, `schemaVersion` 1, and `buildCheckpoint`, `validateCheckpoint(value, { registry, resolveConfig })` reporting every error, hostile-value safe, bounds checked **before** allocation (population size, genome length 159, history length), parameters finite, indices consistent (`generationIndex` equals `history.length`), track ids, versions and hashes checked against the registry, `rngStreams` and `rng.algorithm` equal to this build's, the configuration is checked by an **injected `resolveConfig` adapter** (Codex review: `persistence` may not import `training`, and `training` must stay headless and storage-free, so neither lint boundary is changed). The adapter is a few lines in `src/ui/checkpointAdapter.ts`, the cross-boundary composition layer that already holds `savedReplay.ts`: it wraps `resolveTrainingConfig` (which stays the **one** authoritative set of rules, in `training/`), returning `{ ok, config } | { ok: false, errors }` and never throwing. The format validator knows only the adapter's shape; a test with a fake adapter proves a refusal from it is reported, and a test with the real adapter proves an invalid configuration is refused by the real rules. The RNG state is checked with `restoreRng` from `utils` (an allowed dependency). `eslint.config.js` is not touched, and a test asserts the lint boundaries still hold (the existing architecture tests). Fields: `format`, `schemaVersion`, `id`, `createdAt`, `codeVersion`, `appVersion`, `simulationVersion`, `training` {full configuration, environment, `trackIds`, `trackVersions`, `trackHashes`, `rngStreams`, `rng` {algorithm, words}}, `generationIndex`, `population` {count, order, values}, `champion` (best so far: genome, fitness, generation), `metrics` (below). **Separate from the model format** (a new `docs/CHECKPOINT_FORMAT.md` and a pointer in MODEL_FORMAT.md), so a champion file can never be mistaken for a checkpoint and vice versa; the importers refuse the other's `format` by name.
- **Restored history: an explicit, honest representation (Codex review).** `GenerationStats` carries a per-car fitness list (about 1 KB) and a champion genome (about 4 KB) for every generation, so a complete record cannot be stored for a long run (1,000 generations would be about 5 MB). The checkpoint therefore stores a **history entry** per generation that is one of two shapes: **full** (the whole `GenerationStats`, kept for the most recent K generations (default 20) and for the best-so-far generation) or **compact** (generation, best, mean and worst fitness, `populationSize`, outcome counts, `carsWithLap`, `maxGatesPassed`, `generationTicks`, `totalEpisodeTicks`: everything the graph and dashboard read, and nothing else). Nothing is reconstructed or invented: a compact entry has `fitness: null` and `champion: null`. After a resume, `trainer.record()` returns `generations` as `GenerationStats | CompactGenerationStats` (a discriminated union, `retained: true | false`), so a consumer must handle both: the **graph** and dashboard read only the compact fields (`completedMetrics` takes the population from `populationSize` when `fitness` is null); the **replay picker and the save picker** list a generation with `champion: null` as "champion not kept" and disable Replay and Save for it; the P2 analysis code reads full records only from fresh runs and refuses a compact one with a message. The best-so-far generation is always full, so "best so far" stays replayable and savable.\n- **Size and the byte policy.** A population of 50 is about 160 KB of JSON, so a checkpoint is a few hundred KB at the defaults. One **UTF-8 byte limit** (`MAX_CHECKPOINT_BYTES`, proposed 3 MiB, stated in bytes) at every boundary: after serializing, before parsing on import, on read-back, and for the offered download (compact text when the indented form exceeds it, as in P3-06). A checkpoint that does not fit is **not written** and says so; training continues.
- **`src/persistence/checkpointStore.ts` (new):** injected storage like `modelStore`, **one slot** (`sdae:checkpoint:v1`), every failure a message and never an exception, serialization guarded, and **a failed write leaves the previous checkpoint intact**: localStorage replaces one key's value as a unit, so a `setItem` that throws (quota) keeps the old value, which a test proves with a throwing `setItem`. It never touches `sdae:model:*` keys, and a failed or full store never deletes a saved champion. `read()` returns the validated checkpoint or a reason (none, damaged, newer version, other build); a damaged slot is reported and offered for deletion, never silently overwritten by an automatic save without saying so.
- **Periodic saving while active, and the ordering of every write (Codex review).** At a generation boundary, if training is running (not paused) and either the number of generations since the last save reaches `everyGenerations` (proposed **5**) or `minSeconds` (proposed **30**) of page time has passed, a save is **requested**. All writes go through one small **`checkpointSaver`** (pure given an injected scheduler, clock and store), which owns the rules below, so no code path can write around them:
  - It holds `latest` (the newest boundary state, replaced at every boundary, in memory), `lastWritten` (the generation index last written), a **run identity** (`runId`, new for a fresh start and for each Resume) and an **epoch** (incremented by Resume, Discard and Start fresh).
  - **One pending write at most, coalesced.** Requesting a save while one is pending does not queue another; the pending write is the same callback and it reads **`latest` when it runs**, never a state captured when it was scheduled. It may be deferred (a `requestIdleCallback` or `setTimeout` after the frame, if one save would take more than a frame's budget at the defaults).
  - **Freshness check immediately before every write** (deferred, periodic or hide-time): write only if the saver's `epoch` and `runId` are the ones the request was made under **and** `latest.generationIndex > lastWritten`. A stale callback therefore does nothing.
  - **Hide-time and lifecycle writes cancel the pending write first**, then write `latest` synchronously (if it is newer than `lastWritten`) and set `lastWritten`. A callback that was already released then fails the freshness check. So a queued generation-5 save can never overwrite a generation-6 hide-time save.
  - **Resume, Discard and Start fresh bump the epoch and cancel the pending write** before anything else, so a queued write cannot survive them and replace the newly selected state.
  - The write is **timed and shown**. Autosave stays **off** until the person has answered an unanswered stored checkpoint (see the suspension paragraph below).
- **iOS and browser suspension.** Timers and animation frames stop in a background tab and iOS may terminate the page without any event. The frame loop already resyncs on return. **New:** on `visibilitychange` to hidden and on `pagehide`, write the **latest boundary state held in memory** if it is newer than the last saved one (a synchronous, best-effort `setItem`); the plan claims **no guarantee** of delivery. On the next load, if a checkpoint exists, the page **offers** it ("Resume from generation N, saved <time>" with Resume and Discard buttons); it never resumes automatically and never overwrites it before the person chooses (the first automatic save after a fresh start is allowed only once the person has chosen Discard or Start fresh; until then autosave is off and says so).
- **Quota, unavailable or full storage.** The save status says, in words, that checkpointing failed and why (private window, full) and that training continues, and offers **Download checkpoint**: a file built from the in-memory boundary state, **independent of storage quota or availability**, so a full or private-window store does not block it. It is offered **only when the state serializes within the byte limit** (a state can exceed the cap as the population or retained history grows, or fail to serialize): otherwise the page shows an accurate refusal ("this checkpoint is too large to write out" or "could not be written out"), the **last valid checkpoint is kept** and training continues. The plan does not promise a restorable file when the format cannot emit one, and the same limit applies to import. A failing store is retried at the next periodic point, not every frame.
- **Import and resume from a file (an owner decision, §6; default: included).** A downloaded checkpoint that cannot be loaded back is a weak backup (the same reason P3-06 added import). One file control, the same size-before-read and refuse-without-side-effects rules as P3-06; a valid file replaces nothing until the person confirms Resume.
- **Performance panel.** Extend the opt-in readout (`?debug=fps`, renamed in the user-facing text only if the owner agrees; the flag keeps working) with **mean step time**: the wall time spent inside the simulation step handler per tick (measured with the injected clock around the ticks run in a frame, divided by the ticks run), over the same trailing window and with the same interruption resets as the rate meter; render time is **separate** and reported as per rendered frame; both are reported as "not measured yet" until a window has data, never as a number from nothing. The readout also shows the **recorded context**: population size, track id, render mode (cars drawn, speed mode, replay open) and the build id, so a figure can be quoted with where it came from. The default page is unchanged: the panel is opt-in, adds no work when off, and is covered by the existing "without the flag nothing is published or drawn" tests.
- **Accessibility and layout:** the new status line and buttons live in the existing training block (no new panel); targets at least 44 px; the P3-02 to P3-06 layout and font-stress tests are re-run with the new controls present, in portrait and landscape.

## 5. Why "resume matches an uninterrupted run" is testable

A seeded run of N+M generations is compared with: run N generations, take `checkpointState()`, serialize to text, **parse and validate that text** (so the format is part of the proof), build a **new** trainer from it, run M generations. Because history is lossy beyond the retention window (§4), the contract has **two separately stated parts** (Codex review), never a blanket "the whole record is equal":
1. **Everything the future depends on, and everything produced after the split, is deep-equal and bit for bit** with the uninterrupted run: the restored population, the run generator's state words, and, for each of the M generations run after the resume, the **full** `GenerationStats` (every per-car fitness, the champion genome, outcomes, tick counts), plus the final population and RNG state.
2. **The restored history is compared as a stated projection:** for every generation before the split, the compact fields equal the uninterrupted run's; for the retained generations (the last K and the best so far) the **full** stats are equal; for the others `fitness` and `champion` are `null` and the test asserts they are `null` (not zeros and not copies).
Cases: several seeds; the default population and a small one; both brake settings; splits N=0 and N=1; **and a split beyond the retention window (for example N=25 with K=20, and with a small K in a small test so it is fast)**, which N=0 and N=1 alone cannot exercise; a resume from the real exported **file**; and a resume taken **from a resumed run** (checkpoint, resume, run, checkpoint, resume), so compact entries survive a second round trip unchanged. A third test proves "no cache": the resume is built from exactly the run state words and the population, nothing else. **Scope:** bit-for-bit equality is claimed for the **same supported engine and build** (the checkpoint records `codeVersion`); the simulation uses floating-point math such as `Math.sin`, whose results are not specified to match across JavaScript engines, so the plan does not imply cross-engine equality, and a resume on a different engine is allowed but is not claimed to reproduce the original run.

## 6. Decisions for the owner (defaults proposed; each routine unless changed)

1. **History in a checkpoint:** a **compact** entry for every generation (the fields the graph and dashboard read) and a **full** entry for the **last 20 generations and the best so far**; older generations resume as graph points marked "champion not kept" (Replay and Save disabled), and `trainer.record()` after a resume is a union of full and compact entries (§4).
2. **Periodic cadence:** every **5** generations or **30** s, whichever comes first, at a boundary only, while running.
3. **One checkpoint slot** (the newest), not a list; a new automatic save replaces it only after the person has chosen Resume or Discard for an existing one.
4. **Checkpoint import from a file is included** (default yes), in the same panel.
5. **Size limit** for a checkpoint: **3 MiB in UTF-8 bytes** (stated in bytes everywhere).
6. **Debug flag:** keep `?debug=fps` and show step time and context in the same readout (no new flag).

## 7. Tests

- **Trainer resume (integration, seeded):** §5 in full: both parts of the contract, splits N=0, N=1 and beyond the retention window, both brake settings, two population sizes, resume from parsed-and-validated text and from a real file, and a resume of a resume. A fresh run is unchanged (the existing determinism and golden tests).
- **Format (unit):** every invalid case reported and refused without allocation of an absurd size (population count 1e9, genome length mismatch, `generationIndex` not equal to the history length, `NaN`, `Infinity`, `null`, overflowing exponent, wrong `rngStreams`, wrong algorithm, an invalid `uint32` word, a track hash mismatch, an unknown `format`, a champion file given as a checkpoint and the reverse, hostile values in every position, a deeply nested unknown field, a multibyte near-limit file), with a **byte-for-byte unchanged** store and a spy showing no write.
- **Saver ordering (unit, fake scheduler, clock and store):** a queued generation-5 save, then a hide-time save of generation 6, then the queued callback is released: the slot still holds generation 6 and no write is made; Resume, Discard and Start fresh cancel a pending write and a released stale callback writes nothing; coalescing (many requests, one write, of `latest`); a hide event with nothing newer writes nothing; `runId` mismatch writes nothing; a failing store leaves `lastWritten` unchanged so the next point retries.
- **Dependency path (unit):** the format validator reports a refusal from a fake `resolveConfig` adapter, the real adapter refuses an invalid configuration, and the existing architecture and lint boundary tests pass unchanged.
- **Store (unit, fakes):** round trip; unavailable, quota, full and throwing storage give messages; a failed write **keeps the previous checkpoint intact**; damaged and newer-version slots are reported; saved champions are never touched; serialization failure is a message; the byte limit counts bytes.
- **Page wiring (Node, fakes, fake clock):** periodic saves at the right boundaries only while running; none while paused; a hide event saves the newer in-memory boundary once and not again; nothing resumes automatically; Resume restores history, graph and picker and the run continues as an uninterrupted one would; Discard; failed storage leaves training running and offers the download; step-time and frame-time measurement with an injected clock, including a gap or backwards clock resetting the window and "not measured yet" before data.
- **E2E (Chromium and WebKit, desktop, phone, tablet):** run a few generations, Download checkpoint, reload, Resume from storage, and from the file; the history and the next generation index match; storage denied and full cases; layout with the new controls present at the P3-05 and P3-06 sizes and font-stress cases; the opt-in readout shows step time and context, and the default page publishes nothing extra.
- **Not tested here (manual, below):** real iOS background, resume and termination.

## 8. Owner checks (iPhone and iPad, before a merge request)

1. Start training, let at least 6 generations complete, note the generation number, switch to another app for a minute, return: the page resumes, training continues, and the status says when it last saved.
2. Close the tab (or force-quit Safari) mid-run, reopen the page: it **offers** to resume from a recent generation; Resume continues from it; Discard starts fresh.
3. In a Private tab, either checkpointing works for the session or the page says it cannot, and training keeps running; Download checkpoint works either way.
4. Open the page with `?debug=fps`, note the frame rate, step time, population, track and render mode on the device (model and Safari version), and report them: these are the "named device" metrics. They are observations, not a claim that training is faster or better.

## 9. Limits

A checkpoint is the state of one run at a boundary. It is not a saved champion, not evidence of learning, and not a comparison between runs. Resuming reproduces the **same** run on the same engine and build; it does not claim any result, and a restored history before the retention window is compact by design (no per-car fitness or champion). Browser storage is a convenience, may be cleared, and suspension events are not guaranteed, so Download checkpoint remains the way to keep a copy. The step-time and frame-rate figures describe one device in one condition. ST1–ST5, the held-out evaluation boundaries and all study seeds are untouched.
