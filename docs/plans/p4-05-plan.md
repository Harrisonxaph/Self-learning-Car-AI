# P4-05 plan: evaluate trained models on unfamiliar tracks

> **Status: plan only, for Codex review and the owner's merge. Implementation needs its own owner authorisation.**
> - **Authorisation:** the owner's "Continue development" (2026-11-12, after #165 merged), read as the next Phase 4 step. P4-03 needs P4-05, P4-05 needs P4-04 (merged) and P3-05 (Complete), and P4-06 has its own merged plan but no implementation authorisation. As for earlier items it is read as authorising a **plan only**.
> - **Scope:** the roadmap entry and issue #32: an evaluation runner and UI that runs a saved model on chosen built-in circuits with fixed evaluation seeds and stores the results in the model's `evaluation` field, showing lap completion, collisions and lap time. **Not** in scope: any study (E3, E5, E6, P5-04, P5-05 come from preregistered protocols and the command line, never from this page), custom circuits (P4-03 plugs into the interface defined here), training, any physics change, any learning claim.
> - **Lessons carried from P2-10, P4-04 and the E3 work:** the held-out boundary is the integrity of every generalisation claim, so a page that can show held-out results needs rules that make a breach visible; a deterministic episode repeated is one trial, not many; results are labelled by what they are.

## 1. What P4-05 must deliver (ROADMAP, issue #32)

- **Description:** an evaluation runner and UI that runs a saved model on chosen built-in tracks with fixed evaluation seeds and stores results in the model's `evaluation` field.
- **Acceptance:** **Phase 4 acceptance (part): users can evaluate trained models on built-in layouts they did not train on and see lap completion, collisions and lap time.** Custom layouts are P4-03.
- **Tests:** integration: evaluation deterministic. E2E: evaluate a saved model on a built-in held-out track.
- **MODEL_FORMAT:** each real evaluation entry includes protocol and configuration version, track ID, version and split, frozen model ID, evaluation seeds and starts, episode and outcome counts, metric definitions and summary statistics; absent completed laps give a null lap time with a zero sample count; no traces are embedded.

## 3. Design

- **`src/training/modelEvaluation.ts` (new, pure, headless).** `evaluateModel(model, circuits, options)` evaluates one saved model on a list of circuits under one fixed protocol and returns a plain result. It builds the driver from the model's own recorded `brakeEnabled`, physics and sensors (an A4-type model is evaluated with its brake masked, as trained), runs each episode through `evaluateDriver`, and **never reads a track directly**: circuits arrive as `EvaluationTarget`s (`{ id, version, split, track }`) from the caller, which is how P4-03 later adds saved custom circuits (split `unregistered`) with no change here. Only `src/ui/evaluatePage.ts` and the tests choose targets, through `tracksIn`.
- **The protocol, `p4-05-evaluation-v1`, fixed in code and recorded in every entry.**
  - Limits and scoring: `DEFAULT_EVALUATION_CONFIG` (60 s, 5 s stall, 3 laps, fitness version 1), recorded with a configuration hash.
  - **Starts and evaluation seeds.** A model is deterministic, so the same start repeated is **one** trial, not many (AI_EVALUATION §5). The protocol therefore uses the circuit's nominal start (seed 0) plus **four recorded perturbed starts** (the fixed seed list `[1, 2, 3, 4]`): each is a small offset from the nominal start drawn from the repository's seeded RNG (lateral at most 1.0 m, heading at most 3 degrees), checked to start on the road without touching a wall. The offsets, not just the seeds, are recorded. These starts are scenario variation of one model on one circuit; they are **not** independent training runs and give no uncertainty about training (decision 2 offers the simpler nominal-only protocol).
  - Per circuit the entry holds the **raw rows** (one small row per start: outcome, ordered progress, gates, laps, first-lap time in simulation ticks and seconds, or null) and the **summary**: lap completion (episodes with at least one full lap ÷ episodes), collision rate (episodes ending in a wall collision ÷ episodes), the count of each terminal outcome, mean ordered progress, and mean first-lap time **with its sample count**, `null` and `0` when no lap completed (never zero). Timeouts and stalls stay in every denominator.
- **The entry format and strict validation.** `evaluation` entries get `kind: 'p4-05-evaluation-v1'` with: protocol and configuration version and hash, the model's **frozen identity** (`freezeModel(parameters, provenance)`'s ID), the circuit's ID, version, split and content hash, the seed list and start offsets, the per-start rows and the summary, an `exploratory` flag and, for held-out circuits, `heldOutLook: true`, a `recordedAt` time, the app and code versions, and a `runtime` note ("browser; results can differ slightly between browsers and engines (Math.sin and Math.cos), as AI_EVALUATION §4 says"). `modelFormat` validates **entries of this kind strictly** (finite numbers, counts that add up, the summary recomputed from the rows, the circuit's recorded hash checked against the registry) and keeps accepting every older document: an empty or missing `evaluation` is valid as before, and an entry of an unknown kind is kept opaque (size-capped) rather than refused, so no existing file is rejected. At most 50 entries per model and the existing size limit apply; the format's schema version is unchanged (the field already exists).
- **Held-out circuits in the browser (the main integrity decision).** The acceptance test asks for an evaluation of a saved model on a built-in held-out circuit, so the page can show one, under rules that make a breach visible rather than prevent it:
  1. The model reaches the circuit **only** through `heldOutTrack(id, frozenModel)` (frozen models only), by building the frozen model from the saved parameters and provenance; an unfrozen or edited model is refused.
  2. **One look per frozen model and held-out circuit.** The model's `evaluation` field records the look; asking again **returns the recorded result and runs nothing**. Deleting the entry is not offered. (A browser cannot stop someone clearing storage or importing a model with its entries removed; this makes an accidental repeat visible, not impossible, like the E3 gate.)
  3. It is labelled **exploratory** on the page and in the entry: "an exploratory look, not a study result. If this result changes which model you keep or how you train, these circuits stop being unseen for that model (AI_EVALUATION §5)". The held-out rows need an explicit confirmation tick before Run.
  4. **No held-out figure appears anywhere else:** not on the training dashboard or graph, not in the saved-champions list, not in the comparison view (which never ranks by evaluation results), not in automatic champion selection. The evaluate page shows them only when the user asks.
  5. This page's looks are **not** the preregistered E3, E5 or E6 openings: those happen only through the command line, with its ledger and manifest, on frozen study agents. A user's exploratory look at a built-in held-out circuit does not change a study's integrity (the study agents are different and frozen by hash), and the plan says so on the page and in ARCHITECTURE; it does change what "unseen" means for that user's own model.
- **The page: `?mode=evaluate` (new page mode).** The default page, `?mode=train` and `?mode=edit` are unchanged. A model list (from the model store; a damaged or non-drivable model is shown with its reason and cannot be run), then circuit checkboxes in three labelled groups: **Other training circuits**, **Validation circuits**, **Held-out circuits (exploratory)**, with the circuit the model was trained on marked and not offered as "unfamiliar" (it may be ticked, and is labelled "training circuit"). **Run** evaluates the chosen circuits in short slices (`setTimeout` yields, so the page stays responsive on a phone), with a progress line and a **Cancel** that stores nothing partial; each finished circuit is stored in the model's `evaluation` field through a new `appendEvaluation` store operation that validates the entry and writes it the way a save does (an all-or-nothing write, with the storage-full and disabled-storage messages the saved-champions panel already has). The results table shows, per circuit and split: lap completion, collision rate, outcome counts, mean first-lap time with n, mean ordered progress, and a note that a deterministic model on five starts is one model's behaviour, not a statistic. All controls are at least 44 px and keyboard operable; the table is a real `<table>` with a caption and the status line is a polite live region; nothing scrolls sideways at 320 px.
- **Determinism and replay.** Evaluation is a pure function of the model, the circuit's recorded hash and the protocol, in one engine: running it twice gives identical entries (apart from `recordedAt`), and a test shows that **the stored entry replays**: re-running the protocol on the recorded model, circuit and seed list reproduces every row. Cross-browser differences are recorded, not hidden.
- **No change to the trainer, the split code or the formats beyond the `evaluation` entry kind.** The three-split boundaries and the held-out gate are untouched; the new module is added to the **source-scan allowlist** deliberately (it may call `validationTrack` and `heldOutTrack` through the typed targets only), so a later module reaching for them still fails a test.

## 4. What is deliberately not claimed

Evaluating one model on a few circuits from a few starts shows how that model drove there; it does not show that evolution generalises, that braking helps, or that any rule or baseline is beaten: those are studies (P5-04, E3, E5, E6) with preregistered protocols, ten training seeds and the command line. Perturbed starts are scenario variation, not independent trials. Lap time is simulation time. Held-out circuits viewed here are "unseen" only until the user looks. No learning claim is made.

## 5. Decisions for the owner (defaults proposed; each routine unless changed)

1. **Held-out circuits in the browser as an exploratory, one-look-per-model-and-circuit, confirmed, labelled feature** with the rules in section 3. Alternative: offer validation and other training circuits only and **drop the held-out E2E** (the roadmap's test requirement names a held-out track, so this changes the roadmap's test line and needs the owner's say).
2. **Start protocol:** the nominal start plus four seeded perturbed starts (recommended, so five episodes per circuit show some sensitivity), or the nominal start only (one episode per circuit, simplest, no start variation).
3. **A new page mode `?mode=evaluate`** (recommended) rather than a panel inside the training page, which is already crowded on a phone.
4. **The entry format** `p4-05-evaluation-v1`, strictly validated, with unknown kinds kept opaque and the model schema version unchanged.
5. **Evaluation results never feed the dashboard, the comparison view or automatic selection**, and are never ranked.
6. **At most 50 entries per model**, stored in the model's `evaluation` field in browser storage with the existing safety rules.
7. **The new module on the source-scan allowlist** for the restricted accessors, through typed targets only.

## 6. Tests

- **Unit (`modelEvaluation`):** the protocol's constants; the start perturbations are deterministic for a seed, within the stated bounds and always on the road without a wall touch (checked on **every** built-in circuit and a sweep of seeds); the driver is built from the model's own brake flag (an A4-type model really has its brake masked); the summary equals a hand recomputation from the rows on fixed fixtures (lap completion, collision rate, outcome counts, mean first-lap time with n, `null` and `0` with no completed lap); timeouts and stalls stay in the denominators; hostile models (wrong parameter count, non-finite values, an unfrozen copy) are refused with messages, never a raw exception.
- **Integration (determinism and replay):** evaluating the same saved model twice gives identical entries but for `recordedAt`; a stored entry replays row for row; a tampered row, count, hash or seed list is refused by the validator; every older model file (including the committed fixtures) still imports and its empty `evaluation` is valid.
- **Held-out rules:** a held-out circuit is reached only through `heldOutTrack` with a frozen model; an unfrozen or edited model is refused; a second request for the same model and held-out circuit returns the recorded entry and runs nothing (shown by a call counter); the confirmation is required; no held-out figure reaches the dashboard, the saved list or the comparison view (a source scan and a rendering check); the module appears on the allowlist and nothing else does.
- **Store:** `appendEvaluation` is all-or-nothing, respects the 50-entry cap and the size limit, reports storage-full and disabled-storage, leaves other models untouched, and a model with entries still exports and re-imports identically.
- **Page wiring (Node, fakes) and E2E (Chromium and WebKit, desktop, phone and tablet):** save a champion, open `?mode=evaluate`, evaluate it on the **other training circuit** and a **validation circuit**, see the table, reload and see the stored result; evaluate on a **held-out circuit** (the roadmap's E2E) with the confirmation and see the exploratory label, and see that asking again returns the recorded result without re-running; cancel stores nothing; a damaged model cannot be run; 44 px controls and no horizontal scroll at 320 px.
- **Mutation checks** during implementation: weakening the one-look rule, the frozen-model requirement, the summary denominators, the start bounds and the entry validation each fails a test.
- Not tested here: a physical device, and any statistical claim.

## 7. Owner checks (iPhone and iPad, before a completion request)

1. Save a champion in `?mode=train`, open `?mode=evaluate`, pick it, tick one training and one validation circuit and run: the progress line moves, the table appears, nothing scrolls sideways and the page stays responsive in portrait and landscape.
2. Tick a held-out circuit: the exploratory warning and confirmation are clear; run it; ask again and see the recorded result.
3. Reload: the results are still there; the controls are easy to tap (44 px).

## 8. Limits

One saved model, a handful of circuits and five starts: behaviour, not evidence. A browser cannot enforce the one-look rule against someone who clears storage or edits a file; the rule and the labels make a breach visible. Results can differ between browsers and engines. P4-03 adds saved custom circuits as targets of the same protocol; P4-07 adds camera work that this page does not need. ST1 to ST5, the held-out gate and ledger used by the studies, every existing record and the E3 protocol are untouched.
